# TODO APP

This is a todo application for a single user to maintain a todo list built with React, TypeScript and Node.

## Features

- View and manage a personal ToDo list.
- Create, edit and delete ToDos.
- Mark ToDos as complete or incomplete.
- Hide completed ToDos by default, with an option to show them.
- Maintain task ordering using an ordinal position.
- Assign a due date and time to each ToDo.

## Getting Started

The frontend and backend run independently. Each application has its own dependencies and development commands.

### Prerequisites

- Node.js 24 or later
- npm

NVM is optional. If you use NVM, run `nvm use` from the repository root to select the project's preferred Node.js version.

### Frontend

Install dependencies from the repository root, then run the development server from `frontend/`:

```sh
cd frontend
npm install
npm run dev
```

Vite serves the development app at `http://localhost:5173` by default. Node.js 24 or later is required.

The frontend currently provides a ToDo interface for creating, editing, completing and deleting items. Its data is held in component state only, so it resets on reload and is not yet connected to the backend API.

### Backend

Install backend dependencies and start the development server from the repository root:

```sh
cd backend
npm install
npm run dev
```

The backend listens on port `3008` by default. Set the `PORT` environment variable to use a different port. The `GET /health` endpoint returns HTTP 200 with `{ "status": "ok" }`.

The backend stores ToDos in `backend/data/todos.sqlite`, created automatically at startup. The database directory is excluded from Git.

Run backend checks and create a production build from `backend/`:

```sh
npm run lint
npm run typecheck
npm run build
npm start
```

The production start command runs the compiled JavaScript with Node.js.

### ToDo API

The API is available under `/api/todos`:

| Method   | Endpoint         | Behavior                                                               |
| -------- | ---------------- | ---------------------------------------------------------------------- |
| `GET`    | `/api/todos`     | Returns all ToDos, ordered by ordinal.                                 |
| `POST`   | `/api/todos`     | Creates a ToDo and returns HTTP 201 with the created record.           |
| `PATCH`  | `/api/todos/:id` | Partially updates a ToDo and returns HTTP 200 with the updated record. |
| `DELETE` | `/api/todos/:id` | Deletes a ToDo and returns HTTP 204.                                   |

Create requests require a non-empty `title`; `description` and `dueDateTime` are optional. Due dates must be ISO 8601 UTC values ending in `Z`. PATCH accepts `title`, `description`, `dueDateTime`, and `isCompleted`; omitted fields stay unchanged, and `null` clears description or due date. The backend generates IDs, ordinals, and timestamps. Invalid input returns a structured HTTP 400 response; a valid UUID with no matching ToDo or an unknown route returns HTTP 404. Unexpected server errors are logged and returned as a generic HTTP 500 response. The API returns both completed and incomplete records; visibility filtering is a frontend responsibility.

## Design & Architecture

### Frontend

The frontend is a React, TypeScript and Vite application. The current UI uses component state for ToDos and has not yet been connected to the backend API. Due dates use local time, past due dates are rejected, and deletion requires confirmation.

### Backend

The backend uses Node.js, TypeScript, Express 5 and Node's built-in `node:sqlite` module. Routes, controllers, services and database operations are kept in separate layers. The database is initialized automatically at startup.

### Behaviour & Assumptions

The API returns all ToDos in ordinal order. New items are appended; updates and deletions do not renumber existing items, and a deleted highest ordinal may be reused. Completed-item filtering is not implemented in the frontend yet.

ToDo IDs and timestamps are generated by the backend. PATCH changes only supplied fields. Omitted optional fields remain unchanged; `null`, empty strings and whitespace-only strings clear description or due date. Nonblank values, including surrounding whitespace, are preserved.

### Validation & Error Handling

Titles must contain a non-whitespace character. Due dates must be valid ISO 8601 UTC date-times ending in `Z`. The backend returns structured errors for invalid requests, missing ToDos and unknown routes; unexpected errors receive a generic HTTP 500 response. More comprehensive validation remains future work.

### Testing

The backend has API integration tests using Node.js's built-in test runner and a temporary SQLite database. From `backend/`, run `npm test`. Run `npm run test:report` to generate a JUnit report at `backend/test-results.xml`; the report is excluded from Git.

### AI-Assisted Development

AI development tools are used to support planning, implementation and testing. Technical decisions, generated changes and test results are reviewed and verified as part of the development process.

The repository includes an `AGENTS.md` file containing persistent guidelines for AI coding agents. It defines coding standards, naming conventions, development workflow, testing practices and Git commit conventions to maintain consistency throughout development.

## Known Limitations & Future Work

- Manual ToDo reordering is not currently supported; the backend assigns ordinal positions automatically.
- Deletion is permanent. Soft deletion and recovery may be considered if future requirements justify them.
- The application currently supports a single user; authentication and multi-user support are outside the initial scope.
- Concurrent updates use a last-write-wins approach. Optimistic locking, versioning and more advanced concurrency controls are deferred unless future requirements justify them.
