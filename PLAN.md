# Implementation Plan

## 1. Overview

Build a single-user ToDo application that allows users to create, manage and track tasks, including descriptions, due dates and completion status.

The application will consist of a React frontend and a Node.js backend, with SQLite providing persistent storage.

The implementation will prioritise simplicity, maintainability and a clear separation of responsibilities.

## 2. Functional Requirements

- View a list of ToDos.
- Create, edit and delete ToDos.
- Mark ToDos as complete or incomplete.
- Hide completed ToDos by default, with an option to display them.
- Maintain list ordering using an ordinal position.
- Assign an optional due date and time to each ToDo.

Authentication and support for multiple users are outside the scope of this project.

## 3. Non-Functional Requirements

- Maintain a clear separation between frontend and backend responsibilities.
- Use TypeScript across both applications.
- Implement appropriate input validation and error handling.
- Ensure data persistence and consistency.
- Keep the architecture simple and proportionate to the application's requirements.
- Provide straightforward local development and setup instructions.
- Follow consistent coding, naming and documentation conventions.
- Keep project documentation accurate and up to date as implementation progresses.
- Update README.md alongside relevant changes to features, setup instructions, architecture, behaviour and known limitations.
- Ensure documentation reflects implemented and verified behaviour, rather than planned or assumed behaviour.

## 4. Data Model

The following table defines the initial ToDo data model.

| Field         | TypeScript Type  | SQLite Type | Requirement | Description                                                                               |
| ------------- | ---------------- | ----------- | ----------- | ----------------------------------------------------------------------------------------- |
| `id`          | `string` (UUID)  | TEXT        | Required    | Unique identifier, generated automatically by the backend.                                |
| `title`       | `string`         | TEXT        | Required    | Title of the ToDo.                                                                        |
| `description` | `string \| null` | TEXT        | Optional    | Additional details about the ToDo.                                                        |
| `dueDateTime` | `string \| null` | TEXT        | Optional    | Due date and time, stored as an ISO 8601 UTC string.                                      |
| `ordinal`     | `number`         | INTEGER     | Required    | Position of the ToDo in the list, assigned automatically by the backend.                  |
| `isCompleted` | `boolean`        | INTEGER     | Required    | Completion status, defaulting to `false` (stored as `0` in SQLite).                       |
| `createdAt`   | `string`         | TEXT        | Required    | Creation timestamp, generated and managed by the backend in ISO 8601 UTC format.          |
| `updatedAt`   | `string`         | TEXT        | Required    | Last modification timestamp, generated and managed by the backend in ISO 8601 UTC format. |

### Data Handling

- UUIDs will be generated by the backend and stored as strings in SQLite.
- Due date/time values are validated as ISO 8601 UTC values ending in `Z`; nonblank values are stored as supplied, including surrounding whitespace.
- The frontend will use native JavaScript date handling and display dates in the user's local timezone.
- The backend will generate and manage `createdAt` and `updatedAt`; clients cannot supply or modify these fields.
- SQLite boolean values will be represented as integers (`0` or `1`).

## 5. Architecture & Design Decisions

### Application Architecture

- The project will use a monorepo structure containing independent frontend and backend applications.
- The frontend and backend will communicate over HTTP.
- The frontend will handle presentation and user interactions.
- The backend will own business logic, authoritative validation and data persistence.
- SQLite will be used for persistent storage.
- The backend will use Node.js 24+, Express 5, TypeScript and Node.js's built-in `node:sqlite` module with `DatabaseSync`; no external SQLite package is required.
- The SQLite database will be stored at `backend/data/todos.sqlite`, and its directory will be excluded through `.gitignore`.
- Keep the single-user backend layered into routes, controllers, services and database modules. Routes define endpoints; controllers handle HTTP requests and responses; services apply validation and ToDo behavior; database modules initialize SQLite and run prepared queries.
- Avoid repository patterns, dependency injection frameworks and other abstractions that do not benefit this application.

### Validation

- Both frontend and backend will perform input validation.
- Frontend validation will provide immediate feedback to users.
- Backend validation will remain authoritative, regardless of frontend validation.

### ToDo Ordering

- The backend will assign an ordinal position when a ToDo is created.
- New ToDos will be added to the bottom of the list.
- Editing, completing or reopening a ToDo will not change its ordinal position.
- Deleting a ToDo will not cause remaining items to be renumbered.
- Manual reordering is outside the initial scope.

### Completed ToDos

- Completed ToDos will be hidden by default.
- Users will have the option to display completed ToDos.
- Changing completion status will not affect the ToDo's ordinal position.

### Timestamps

- Timestamps will be stored as ISO 8601 UTC strings.
- `createdAt` and `updatedAt` will be managed by the backend.
- `updatedAt` will be refreshed when a ToDo is modified.
- Clients cannot directly supply or modify system-managed timestamps.

## 6. Implementation Plan

### Stage 1: Project Bootstrap

Establish the foundational project structure and development environment.

- Use a monorepo with independent `frontend/` and `backend/` applications, each with its own `package.json`, `package-lock.json`, dependencies and development scripts. Do not use npm workspaces or a root package manifest.
- Use Node.js 24 as the preferred development version, identified by a root-level `.nvmrc` containing `24`. Declare Node.js `>=24` under the `engines` field in both `frontend/package.json` and `backend/package.json` to communicate runtime compatibility and allow npm to warn when the requirement is not met; this does not enforce installation. NVM is optional.
- Build the frontend with React, TypeScript and Vite, using Vite's default development port (5173), an independent TypeScript configuration, and ESLint configured for React and TypeScript. Implement a basic Hello World page.
- Build the backend with Node.js, TypeScript and Express 5, using port 3008 by default with configuration through `PORT`. Provide `GET /health`, returning HTTP 200 with `{ "status": "ok" }`. Use an independent TypeScript configuration and ESLint configured for Node.js and TypeScript.
- Use `tsx` as a backend development dependency for TypeScript execution and watch mode. Use `tsc` for type checking and production compilation; run compiled JavaScript with Node.js in production.
- Include ESLint for both applications; do not include Prettier at this stage.
- Maintain `README.md` alongside implementation with actual installation and development commands, runtime requirements, ports, project structure and health endpoint. Distinguish planned features from implemented behaviour and document verified behaviour.

Further implementation stages will be defined as requirements and design decisions are established.

### Stage 2: Core ToDo Management (Implemented)

Implement the core ToDo CRUD API in the layered backend described above. Stage 2 uses the existing Node.js 24+, Express 5, TypeScript and ESLint setup, with built-in `node:sqlite` `DatabaseSync`; it adds no dependencies or automated test tooling.

- Initialize `backend/data/todos.sqlite` on server startup and create the `todos` table when it does not exist. Exclude `backend/data/` through `.gitignore`.
- Store `id`, `title`, `description`, `dueDateTime`, `createdAt` and `updatedAt` as SQLite `TEXT`; store `ordinal` and `isCompleted` as `INTEGER` (booleans use `0`/`1`). Optional description and due date values may be `NULL`.
- Generate UUIDs with Node.js `crypto.randomUUID()` and create backend timestamps with `Date.toISOString()`.
- Validate due date/time strings as ISO 8601 UTC values ending in `Z`. Store accepted nonblank values exactly as supplied, including surrounding whitespace.
- Use prepared SQL statements for list, insert, update and delete operations. A single insert statement computes `COALESCE(MAX(ordinal) + 1, 0)` and creates the row; update and delete each use one statement, so Stage 2 does not require a multi-statement transaction.
- Implement `GET /api/todos` to return completed and incomplete ToDos ordered by ordinal; visibility filtering belongs to the frontend.
- Implement `POST /api/todos` to create a ToDo with a generated UUID, ordinal, timestamps and `isCompleted: false`.
- Implement `PATCH /api/todos/:id` for partial updates to `title`, `description`, `dueDateTime` and `isCompleted`. Omitted fields remain unchanged; clients cannot update `id`, `ordinal`, `createdAt` or `updatedAt`.
- Implement `DELETE /api/todos/:id`. Updates and deletions do not change remaining ordinals; if the highest ordinal is deleted, its value may be reused.
- Basic validation rejects missing or invalid required fields, unsupported field types, empty PATCH bodies, and invalid UUID syntax with HTTP 400. Valid UUIDs without a matching ToDo return HTTP 404.
- For optional description and due date values, omitted POST fields default to `NULL`; omitted PATCH fields remain unchanged; explicit `null`, empty strings and whitespace-only strings are stored as `NULL`. Nonblank strings are preserved exactly. Titles must contain a non-whitespace character and are also preserved exactly; no title or description length limits are imposed.
- Update `README.md` with the API, database location, setup instructions and verified behavior. Run typecheck, lint and build checks and manually verify CRUD and basic 400/404 behavior. Automated testing is deferred to Stage 3.

### Stage 3: Validation and Robustness

Keep Stage 3 proportionate to the single-user application. Use Node.js built-ins and the existing `tsx` dependency; do not add packages or backend architecture layers.

- Require POST and PATCH bodies to be present JSON objects. Reject missing bodies, arrays, primitives and `null` with HTTP 400.
- Reject unknown fields. POST accepts `title`, `description` and `dueDateTime`; PATCH also accepts `isCompleted` and must contain at least one supported field.
- Require titles to be nonblank and validate supported field types. Validate due dates as ISO 8601 UTC date-times ending in `Z`, including calendar and time validity. Preserve Stage 2 whitespace behavior and optional-field semantics.
- Return the first detected validation error. Do not add maximum title or description lengths, a custom request-size limit, or special unsupported-content-type handling at this stage.
- Use one central Express error middleware and a small structured response: `{ "error": { "code": "...", "message": "..." } }`. Error messages shown to users should be clear and user-friendly; do not expose internal details. Controllers pass errors through; services handle validation and business logic. Use Express 5 error propagation and log unexpected errors.
- Return `VALIDATION_ERROR` with HTTP 400, `TODO_NOT_FOUND` or `ROUTE_NOT_FOUND` with HTTP 404, and `INTERNAL_SERVER_ERROR` with HTTP 500. Unsupported methods use the route-not-found response; do not add 405 handling or `Allow` headers. Keep `GET /health` returning HTTP 200 while the server is running.
- Database directory creation, opening or schema initialization failures must prevent server startup. Runtime database failures use the central HTTP 500 response. Do not add special busy/locked handling.
- Keep the existing single-statement maximum-plus-one ordinal assignment and allow reuse after deleting the highest ordinal. Do not add a unique ordinal index. Editing, completing or reopening a ToDo must not change its ordinal; `createdAt` remains immutable and `updatedAt` refreshes on every successful PATCH, including unchanged values. Timestamps remain backend-generated UTC values. Deletion remains permanent, and updates use last-write-wins without locks, queues or versioning.
- Add a focused API integration test suite using Node.js `node:test`, `node:assert` and existing `tsx`. Use a temporary SQLite database so tests cannot modify development data. Cover representative CRUD, validation and not-found responses, persistence, ordering, timestamps and concurrent creation. Do not add separate exhaustive boundary or rare database-failure suites.
- Update `README.md` with the implemented error behavior and test command. Run typecheck, lint, build and the focused test suite.

### Stage 4: Frontend Integration and ToDo UI

Implement the ToDo frontend using the existing React, TypeScript and Vite setup.

- Build and review the UI with React component state first, then connect it to the backend API.
- Integrate with the existing backend API using native `fetch`.
- Implement ToDo listing, creation, editing, deletion and completion.
- Hide completed ToDos by default, with an option to display them.
- Handle due dates in the user's local timezone and prevent setting a due date in the past.
- Confirm permanent deletion before removing a ToDo.
- Validate the title and due date as the user changes them, and disable saving while the form is invalid. Backend validation remains authoritative.
- Refresh the list when an API operation reports that a ToDo no longer exists. Show delete failures in a browser alert.
- Provide user-friendly error feedback.
- Use semantic HTML and basic accessibility practices.
- Apply minimal, responsive styling focused on readability and usability.
- Keep the implementation simple. Do not add dependencies, state-management libraries or unnecessary architecture layers.

### Stage 5: Testing and Finalisation

- Verify frontend and backend integration and core user flows.
- Test validation, error handling and date/time behavior.
- Check basic accessibility and responsive usability.
- Run lint, typecheck and production build checks.
- Update `README.md` to reflect the completed application.
